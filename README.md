# Telegram Shop Bot — فارسی / English

ربات فروشگاهی تلگرام با معماری مناسب Render + Supabase.

## امکانات
- فارسی و English با انتخاب زبان
- Flask + Telegram Webhook
- Supabase PostgreSQL
- پنل مدیریت داخل تلگرام با نقش‌ها
- دسته‌بندی چندسطحی و کاتالوگ
- عکس، توضیح، قیمت، موجودی
- سبد خرید
- Telegram Stars
- کارت‌به‌کارت با ثبت رسید
- درگاه آنلاین با ساختار قابل اتصال (زرین‌پال)
- فاکتور و سفارش
- کانال اجباری
- تایید سفارش توسط ادمین
- کوپن تخفیف
- کیف پول داخلی
- امتیاز کاربر
- آمار فروش
- پیام‌رسانی گروهی
- قیمت‌گذاری تبلیغات کانال/بنر
- پیگیری وضعیت سفارش
- تیکت پشتیبانی
- ارسال خودکار فایل/کد برای محصولات دیجیتال پس از پرداخت
- پنل مدیریت وب ساده

## ساختار
- `app.py`: Flask و Webhook
- `bot.py`: منطق Telegram
- `db.py`: دسترسی Supabase
- `services.py`: منطق فروشگاه
- `config.py`: تنظیمات
- `schema.sql`: جداول Supabase
- `templates/admin.html`: پنل وب
- `render.yaml`: تنظیمات Render

## نصب
1. این پروژه را در GitHub قرار دهید.
2. در Supabase یک پروژه بسازید و کل فایل **`schema_update.sql`** را یک‌بار در SQL Editor اجرا کنید (روی دیتابیس خالی هم کار می‌کند و چندبار اجرا کردنش بی‌خطر است). ربات باید با کلید **service_role** وصل شود.
3. Environment Variable های فایل `.env.example` را در Render تنظیم کنید.
4. سرویس Render را به GitHub وصل کنید.
5. بعد از Deploy، آدرس:
   `https://YOUR-SERVICE.onrender.com`
   را در `BASE_URL` بگذارید.
6. آدرس webhook:
   `https://YOUR-SERVICE.onrender.com/telegram-webhook`
   باید توسط ربات تنظیم شود. برنامه در startup این کار را انجام می‌دهد.

## نکته مهم درباره Sleep در Render
وقتی سرویس Free به خواب می‌رود، ارسال یک Update از Telegram به endpoint وبهوک باعث درخواست به سرویس می‌شود و Render می‌تواند آن را بیدار کند. بنابراین کاربر لازم نیست جداگانه سایت را باز کند؛ اولین پیام/کلیک Telegram خودش درخواست webhook ایجاد می‌کند. این موضوع وابسته به رفتار فعلی پلن Render است.

## اجرای محلی

## 🆕 نسخه‌ی جدید: محصول فیزیکی (پستی) + دیجیتال، سفارش‌ها، سبد خرید هماهنگ

### جریان کاربر: زبان ← پنل ← صفحه‌ی اصلی
- اول زبان (فارسی/English) پرسیده می‌شود، بعد پنل (مشتری/فروشنده/مالک). تا زبان انتخاب نشده هیچ بخشی باز نمی‌شود.
- کسی که از لینک فروشگاه وارد شود مشتری است و سؤال پنل برایش رد می‌شود و مستقیم وارد همان فروشگاه می‌شود.
- تغییر زبان از منو، دیگر پنل را دوباره نمی‌پرسد.
- همه‌ی پیام‌ها (حتی اعلان‌هایی که برای طرف مقابل می‌روند) به زبان **گیرنده** ارسال می‌شوند؛ تاریخ در فارسی شمسی و ارقام فارسی است.

### نوع محصول
هنگام افزودن محصول، فروشنده نوع را انتخاب می‌کند:
| نوع | رفتار |
|---|---|
| 💾 دیجیتال | بعد از تایید پرداخت، فایل/کد به‌صورت خودکار برای خریدار ارسال می‌شود. سفارش «تکمیل‌شده» می‌شود. |
| 📦 فیزیکی | آدرس تحویل گرفته می‌شود، موجودی کم می‌شود، فروشنده سفارش را با پست می‌فرستد و کد رهگیری ثبت می‌کند. |

### شیوه‌ی پرداخت = تصمیم فروشنده
- ⭐ استار: فاکتور استار تلگرام (مبلغ بر اساس قیمت استاری که فروشنده تعیین کرده).
- 💬 سفارشی: گفتگوی ناشناس بین خریدار و فروشنده؛ فروشنده بعد از دریافت پول «پرداخت شد» را می‌زند.
- سبد خرید به‌ازای **هر فروشنده و هر شیوه‌ی پرداخت** جدا می‌شود و هر گروه یک سفارش مستقل دارد (پول و کالای دو فروشنده هرگز قاطی نمی‌شود).

### آدرس و ارسال پستی
- نام، موبایل، آدرس و کد پستی گرفته و اعتبارسنجی می‌شود؛ آدرس ذخیره می‌شود و دفعه‌ی بعد با یک دکمه استفاده می‌شود.
- آدرس و **تعداد** فقط برای فروشنده‌ی همان سفارش (و مالک) نمایش داده می‌شود و فقط **بعد از تایید پرداخت**.
- فروشنده: «🚚 ثبت ارسال» ← کد رهگیری ← خریدار پیام می‌گیرد و «✅ دریافت کردم» را می‌زند.
- فروشنده/مالک می‌توانند سفارش پرداخت‌شده‌ی ارسال‌نشده را لغو کنند؛ پرداخت استاری **خودکار برگردانده** و موجودی بازمی‌گردد.
- منوی «🚚 مدیریت سفارش‌ها» برای فروشنده (سفارش‌های فروشگاه خودش) و مالک (همه‌ی سفارش‌ها).

### نظر و گزارش
- هر نفر برای هر محصول **۱ نظر** و **۲ گزارش** (با `REVIEW_LIMIT` و `REPORT_LIMIT` قابل تغییر؛ حداکثر ۲). محدودیت در دیتابیس هم اعمال می‌شود.
- فقط خریداران واقعی نظر می‌دهند (`REVIEW_REQUIRES_PURCHASE=0` برای غیرفعال‌کردن). فروشنده برای محصول خودش نظر نمی‌دهد.
- هر گزارش جدید برای مالک پیام می‌شود.

### امنیت و پایداری
- وبهوک: هدر secret الان **اجباری** است (قبلاً درخواست بدون هدر هم رد می‌شد، یعنی `successful_payment` جعلی ممکن بود). آپدیت تکراری هم پردازش نمی‌شود.
- پرداخت استار: جلوگیری از پرداخت/تحویل دوباره (ثبت `charge_id` + تغییر وضعیت اتمیک)، بررسی مبلغ، بررسی موجودی در pre-checkout، و بازگشت خودکار وجه در شرایط ناهمگون.
- متن‌های کاربر (نام، آدرس، نظر...) در پیام‌های HTML امن‌سازی می‌شوند (قبلاً می‌توانست پیام را خراب کند یا لینک تزریق کند).
- دکمه‌های تایید پرداخت/معامله فقط برای فروشنده‌ی همان سفارش یا مالک کار می‌کنند و فقط یک‌بار.
- فرم‌های نیمه‌کاره (آدرس، افزودن محصول...) با ری‌استارت Render گم نمی‌شوند (`bot_states`)؛ گفتگوی ناشناس هم بعد از ری‌استارت ادامه پیدا می‌کند.

### اصلاحات کوچک روی منطق قبلی (چون با قابلیت‌های جدید تداخل داشتند)
1. پنل وب (`/admin`) خطای 500 می‌داد چون قالب‌ها در `templates/templates/` بودند؛ نسخه‌ی درست در `templates/` اضافه شد.
2. متن فرم‌ها (نام فروشگاه، نام محصول، نظر...) اگر شامل کلماتی مثل «سفارش»/«کانال» بود به‌جای ذخیره، منو را باز می‌کرد؛ حالا فقط دکمه‌های واقعی منو وسط فرم حساب می‌شوند.
3. آمار فروشنده‌ها (`admin_sales`) حالا فقط سفارش‌های **پرداخت‌شده** را می‌شمارد.
4. محتوای دیجیتال بدون تفسیر HTML ارسال می‌شود (کدهایی با `<` یا `&` قبلاً ارسال را می‌شکستند).
5. دکمه‌ی «افزودن به سبد» در صفحه‌ی محصول وجود نداشت؛ اضافه شد (+ دکمه‌های ➕/➖ تعداد).
